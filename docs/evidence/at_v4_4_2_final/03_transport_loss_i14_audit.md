## First divergence: LAYER A (harness established-marker) — VALIDATION_OBSERVABILITY_FAILURE

Evidence:
- The `adb shell` interactive entry output on THIS device is:
      "adb shell\nconnected\nHNALI-Q:/ $ "
  i.e. the connection status line is `connected` with NO `[adb] ` prefix, followed
  by the remote prompt `HNALI-Q:/ $ `.
- i14's waiter gated on `observed.contains("[adb] connected")` ONLY. That marker
  never matched the device's actual `connected`, so `established` stayed false.
- Consequence: the waiter NEVER entered the `if (established)` block, so `id` was
  never sent, `uid=2000` was never produced, no transport loss was injected, and
  no `AFTER_TRANSPORT_LOSS` was observed.
- The raw i14 output `out=[adb shell\nconnected\nHNALI-Q:/ $ ]` is exactly the
  state at the moment `established` failed to flip: the remote shell WAS reached
  (A is actually TRUE), but the harness mis-detected it.

Contrast: runInteractive() (used by i1-i7, all PASS) gates established on
  `"[adb] connected" || "$ " || ":$"` (loose), which DOES match this device.
i14 used the strict single marker. This is the divergence.

Classification:
  TRANSPORT_SEMANTICS_FAILURE   = NO  (A is reached; B/C/D are never exercised
                                        because A's harness gate mis-fires)
  VALIDATION_OBSERVABILITY_FAILURE = YES (harness established-marker mismatch)

## Minimal TEST/HARNESS-only repair applied (AdbCliInteractiveTest.kt, i14 only)
1. established marker aligned to device reality:
     `snap.contains("connected") || snap.contains("$ ") || snap.contains(":$")`
   (same loose predicate as runInteractive()).
2. After sending `id`, explicitly confirm `uid=2000` is observed BEFORE injecting
   transport loss (so we only test loss on a session that is truly in the remote
   shell). If uid=2000 is not seen, restore WD and return (no vacuous pass/fail).

This repair touches ONLY the androidTest harness. It does NOT modify:
  - Product semantics / ADB protocol / TLS / shell-v2 / recovery ownership.

## Environment blocker preventing a green i14 THIS round (NOT a Product regression)

After the harness repair, i14 was re-run. The new failure is:
  "adb shell\npairing required: no ADB identity found\n..."

Root cause (toolchain/environment, not Product):
  - On this HONOR device, `adb install -r` (which Gradle connectedDebugAndroidTest
    performs) RESETS the app's private data. Each instrumentation run therefore
    starts with a FRESH app identity.
  - Observed fingerprints across installs (all distinct):
        64d3d804...  (the Controller-authorized first-use paired identity)
        a7431290...  (generated by a subsequent install -r, untrusted)
  - A fresh untrusted identity cannot connectAuto -> `adb shell` reports
    "no ADB identity found" / pairing required.
  - Making a fresh identity trusted requires a NEW pairing, which AT.V4-4.2D
    forbids: "No further Product pairing is allowed during this installation
    lifecycle."

Therefore i14 CANNOT reach a green result this round without either:
  (a) a second Product pairing (forbidden), or
  (b) an install strategy that preserves app data across the instrumentation run
       (toolchain change, out of scope / would change the verified install model).

The harness repair is correct and will make i14 observability-correct ONCE a
trusted identity is present. The remaining blocker is purely the install-resets-
identity environment behavior colliding with the single-pairing constraint.
